# 03: The client interface and its in-memory implementation

**What to build:** One interface describing what a participant can do, and an in-memory implementation of it that the UI can render against. This is the seam that makes the transport swappable and makes the whole data layer testable without a server. After this ticket, a screen can read boards, threads and entries and post a message — still entirely in the browser, with no server functions yet.

Three things a reviewer found missing here are load-bearing, and fixing them after ticket 06 means a seam rewrite:

- **The two participant reads.** `read:member` is its own permission, so a board's participants must be a read of their own — and the prototype leaks `board.members` off the board payload, which would hand every caller exactly what that permission withholds. Both reads belong in the interface now.
- **The entry shape.** Ticket 10a widens a thread's contents from messages to four kinds of entry. If the interface freezes `Message` here, that widening is a five-file refactor; if `Entry` is a union of one member today, it is an addition later.
- **`subscribe`'s transport.** The stream is a server route, not a server function (ticket 11a). The interface declares `subscribe`; the HTTP implementation cannot honour it until 11a and must say so loudly rather than return an empty subscription.

**Blocked by:** 02c — The demo seed, with an origin on everything

**Write scope:** `src/client/**` — the interface, the in-memory implementation, and the two conformance suites. Later tickets add operations to this interface; this ticket establishes its shape and the two-file suite split.

**Status:** done — verified, see `## Comments`

- [x] A single `RelayboardClient` interface exists and is the only thing the UI is allowed to depend on for data.
- [x] The interface carries the prototype's nine operations plus the operations the model requires: reading a thread as a chronology, listing a board's resources, attaching a resource, moving a status, acknowledging, and reading each principal's position.
- [x] **The interface carries the two participant reads**: a board's participants, and one participant **with the grant it holds on that board** — so the second read takes both a principal and a board, because a grant is per board and a read that took only an id could not answer "what may this participant do here". Gated by `read:member`. It is `readPrincipal({ principalId, boardId })` returning `{ principal, grant, declared }`: `principal` is the record, whose derived issuer and fingerprint arrive with 08c and are computed from the credential then rather than seeded, `grant` is what it may do on that board and nothing outside it, and `declared` holds the operator and reason the principal asserted and nothing verified — separate rather than merged, so a client can still label the declared strings as declared.
- [x] **`listBoards` returns a member *count* per board and not a member list**, so the permission that withholds a board's participants is not defeated by the call that lists boards.
- [x] **A thread's contents are typed as a union with one member today**, so ticket 10a adds kinds rather than replacing a type that three later tickets have already frozen.
- [x] Admission and permission administration are **not** members of this interface; they live on a separate surface.
- [x] `subscribe` is declared with its event vocabulary, and the in-memory implementation drives it from the store.
- [x] An in-memory implementation satisfies the interface by delegating to the store, and is the only implementation in this ticket.
- [x] A conformance suite is written against the interface, not against the implementation, and passes against the in-memory client.
- [x] **The suite is two files, not one**: an operations suite covering everything except the stream, and a stream suite covering `subscribe` and its event vocabulary. The two transports arrive at different tickets — operations over HTTP in 06c, the stream over SSE in 11a — so 06c must be able to skip the stream suite explicitly rather than weaken the operations suite to accommodate a transport that does not exist yet. They are `tests/contract/operations.conformance.ts` and `tests/contract/stream.conformance.ts`: the operations file runs against the in-memory client from this ticket, and the stream file is marked **skipped pending 11a** — skipped rather than absent, so its existence is visible from this wave and 11a turns the skip into a run rather than writing the file from scratch.
- [x] The conformance suite asserts only caller-observable behaviour: no assertion names a store field, a `cursors` object, or any internal. Where a criterion needs one progress position, it asks through `readPositions`.
- [x] Every operation that requires a grant declares which one it requires; the check itself arrives in 07a.

## Comments

**Implemented and verified** at `f95c8c5`. One interface, one in-memory implementation, and a suite written against the interface rather than against the implementation — which is the whole point of the ticket, because 06c has to point the same file at an HTTP client without editing a line of it.

What was checked rather than assumed:

- `clientOperations` is the literal **18** members as this ticket left it — **19 since 06b added `readActingPrincipal`**, which is the one operation whose permission is `none` because a caller with no session must be able to ask who it is acting as (spec L325–341). The suite's sorted-list assertion was extended with that name in the same change, so the count moved for a stated reason rather than by drift. It also asserts that `knock`, `pollAdmission`, `listPending`, `admit`, `deny`, `revoke`, `grant` and `editGrant` are **not** among them — so "admission and permission administration live on a separate surface" is a failing test rather than a description.
- `operationPermissions` is exhaustive **by type**: `Record<ClientOperation, PermissionName | null>` means an operation added without a line here does not compile, and the suite asserts the same fact as data. The declared requirements are checked against the literal fifteen, and `setConnection`/`subscribe` are the only two that are `null` (a predicate, not a name — `read:board` on at least one board).
- `listBoards` returns `BoardSummary`, which is `DomainBoard & { memberCount }`: the count is beside the record, and the suite pins both halves at the type level with `expectTypeOf` so a `members` array cannot reappear on either the interface's return type or the domain record.
- The entry union is one member today and every consumer is typed against `Entry`: `readMessages`, `readThread`'s `ThreadContents`, and the stream payloads all name `Entry`, so 10a widens a union rather than replacing a type.
- `readPrincipal({ principalId, boardId })` returns exactly `{ principal, grant, declared }`, asserted as three keys and as an exact type, with `grant.scope` pinned to `"board"`. A transport that merged the declared strings into the principal record would fail here rather than at 12.
- **One correction to this ticket's own wording, made while verifying it.** Criterion 3 originally read as though `principal` already carried the derived issuer and fingerprint. It does not and cannot: those are 08c's derived values, computed from the credential the workspace issued, and the domain `Principal` gains them there. The criterion now says the read returns the record *and* that the derived pair arrives with 08c, which is what the interface and the in-memory client actually do — `declared` carries the description today and gains the operator and reason at 08a.
- The commit records `npm test` at 116 passed and 6 skipped, `check` over 27 files, `check:styles`, `typecheck` and `build` all exit 0, with the build still `node-server`. Independently re-run once this ticket's file was written: `npm test` in the app reports **116 passed, 6 skipped, 5 files**, and `npm run app:check` at the root exits 0. That re-run was on a tree that also carried 04a's in-flight, uncommitted files, so `check` counted 37 files rather than 27 — the suite count and the gates are this ticket's; the file count is not.

**Three placeholders that throw rather than return a stub.** `attachResource`, `moveStatus` and `acknowledge` are on the interface because establishing its shape is this ticket's job, but the entry-writing path reaches 10a. Each throws `NotYetImplementedError` naming `ticket 10a`, and the conformance suite asserts the loud failure (`rejects.toThrow(/10a/)`) instead of a success path. The rule is 06a's — an absent feature must fail loudly rather than read as a pass — and when 10a lands these become success-path assertions. That is the intended alarm, not an inconvenience: a stub returning a plausible entry would have been indistinguishable from a working act.

**The grant the demo client reports is a stand-in in one constant.** Until 07a lands real grants, `grantOn` derives a principal's permissions from board membership and returns `MEMBER_PERMISSIONS` — everything the prototype let a member do on its board (`app.js` L140–160 reads, L178 posts), expressed as the spec's named permissions and scoped to `"board"` so nothing here can become a workspace-wide capability. It is one constant in `src/client/in-memory.ts` and 07a deletes it when it replaces the predicate with a grant lookup. Two consequences a later ticket should know: the client does **not** check permissions (07a's check runs at the boundary, and a copy here would be a second place to disagree with it — this ticket only *declares* them), and the superadmin `nadia` therefore reports an empty grant, which is honest for a principal that holds no grant yet.

**`readThread` advancing `seen` is what makes the ladder observable at all.** Reading a thread is the only act that should count as reading, so `readThread` calls `store.markRead` and `readMessages` does not — which is why the suite can assert, through `readPositions` alone, that a reader's `seen` moves and nobody else's does. Without that one call, "pausing advances neither, resuming advances `cursor` only, reading advances `seen` only" (02b) would be unobservable from the interface, and 11b's unread badge would have nothing to count from.

**Two smaller decisions worth recording.**

- **`subscribe` carries nine names, not eight.** The eight are the wire vocabulary 11a asserts as a literal set; `stream-error` is *client-reported* when the transport fails, so it can never be emitted by a server route. `WireStreamEventType` excludes it, so 11a's assertion cannot be broken by the interface's own shape.
- **`setConnection` is a no-op returning the current `StreamState`**, with `pending` derived from the cursor rather than a counter (11b:17). The store *does* have a real pause primitive with tests (02b); the client deliberately does not call it, because pause is the reader's state and delivery belongs to the stream. 11b's panel is the first consumer that must decide whether pausing the view calls the store primitive or stays local — see 02b's Comments for the same note from the store's side.
- **The stream file is skipped, not absent**: `tests/contract/stream.conformance.ts` declares the six cases 11a's criteria name and `tests/client.test.ts` calls it, so "the stream is not tested yet" appears as `6 skipped` in every run rather than as silence. 11a removes the `.skip` and fills the bodies.
